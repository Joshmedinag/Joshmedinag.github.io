Three decisions behind the tool.

Structure before assumptions

Channels and metadata establish how each AOV is handled. Colour, technical, Cryptomatte and unknown data retain appropriate diagnostics without forcing one interpretation onto every pass.

Find the exact frame

Robust temporal statistics expose unusual luminance changes. Charts, an ordered Outliers view and Locate Selected Frame connect an aggregate warning to its evidence.

Ready for automation

GUI and CLI share the same typed models, while strict reports, baseline comparison, deterministic exit codes and bounded discovery support publishing checks.

Historical benchmark and current limits

A controlled benchmark used 12 generated 320 × 180 frames, five AOVs and 30 repetitions per strategy on one Windows workstation. Frame-first processing reduced application-level reader calls from 60 to 12 while preserving the output checksum. Median elapsed time changed from 0.4387 s to 0.1181 s; Python-tracked peak memory increased from about 5.55 MB to 11.08 MB.

The result supports this processing change under those conditions. Native decoder allocations were not fully measured, and the timing ratio is not a general production-performance claim.

A separate in-memory scalability check processed 100, 500 and 1,000 frames in approximately linear time for its small 64 × 36 fixture, reaching 0.505 seconds and 2.206 MB of Python-tracked peak memory at 1,000 frames. It excludes OpenEXR decoding, filesystem I/O and full-resolution native allocations.

These measurements predate 1.4.0rc1 and are not a current candidate benchmark. The current candidate supports flat multipart EXRs with separate part identities and windows; any deep part or incomplete decode rejects the whole frame. Memory admission is an estimate, not an operating-system RSS cap. Frame deadlines exclude parent discovery, final rules and export. Cryptomatte classification depends on standard metadata or an explicit preset.

Implementation details and safeguards

Technical checks, made repeatable.

I designed and developed AOVGuard to inspect rendered EXR files and identify common technical problems before they reach later stages of a lighting or compositing pipeline. It gives lighting and compositing artists a repeatable review of a file or sequence, with a finding linked to the exact AOV, channel or frame that needs attention.

The documented implementation automatically inspects EXR parts and channels, normalises colour passes to a canonical RGB convention and diagnoses technical AOVs per channel. Standard Cryptomatte metadata keeps encoded IDs out of luminance and temporal-outlier calculations while preserving integrity checks.

A shared report model serves the PySide6 interface, command line, strict JSON and self-contained HTML exports. The 1.4.0rc1 candidate adds estimated memory admission, isolated frame execution, optional technical ranges and protected report publication. These safeguards do not turn statistical warnings into artistic approval.

Toolkit

Python 3.11/3.12 · OpenEXR · NumPy · PySide6 · pytest

What I developed

  • Automatic inspection of regular and multilayer EXRs, with colour, scalar, vector, mask, depth, Cryptomatte and unknown AOV categories.
  • Frame-first processing with float64 accumulation, every physical channel preserved and independent identities and windows for flat multipart EXRs.
  • Configurable checks for NaN/Inf, negative and extreme values, empty passes, constant channels, missing AOVs, mixed resolutions and structural changes.
  • Sequence discovery with filename patterns, recursive search, bounded depth, frame limits and inclusive expected ranges for missing heads, tails and internal gaps.
  • Median/MAD temporal analysis, luminance and change charts, score-ordered outlier review and direct navigation to the exact frame evidence.
  • One canonical report for GUI, CLI, JSON and HTML output, with baseline comparison and protected atomic exports that allow retry without reanalysis.
  • Optional per-frame memory admission and technical range policies, plus default CLI/GUI isolation, frame deadlines, cancellation, restart and fail-closed cleanup.
Review workflow: inspect, analyze, export
  1. 01

    Select a file or render folder.

  2. 02

    Inspect channels, parts and inferred AOVs.

  3. 03

    Set rules, discovery limits and the expected range.

  4. 04

    Analyze and filter findings by severity or text.

  5. 05

    Review metrics, temporal changes and outliers.

  6. 06

    Export canonical JSON or self-contained HTML.

  7. 07

    Compare the result with a previous baseline.

One report model, every interface.

The architecture keeps discovery, reading, analysis and presentation separate while the CLI, GUI and exporters share the same report.
